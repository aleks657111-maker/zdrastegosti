## Подробности по каждому багу

### Баг №1 (Major) — :hover и .active в меню-навигации визуально идентичны

Файл: menu.css, строки 65-75.

    .menu-jump-row a:hover {
      background: var(--red);
      border-color: var(--red);
      color: var(--cream);
    }

    .menu-jump-row a.active {
      background: var(--red);
      border-color: var(--red);
      color: var(--cream);
    }

Оба правила задают одинаковый набор свойств с одинаковыми значениями. Пилюля, на которую пользователь просто навёл курсор мышью (без прокрутки/клика), выглядит абсолютно так же, как единственная реально «активная» (выставляемая логикой menu.js) пилюля. Если в момент скриншота курсор находится над одной пилюлей, а реальная активная секция (.active, выставляемая JS) — другая, пользователь видит два одинаково окрашенных зелёных элемента и закономерно интерпретирует это как баг «подсвечивается не то» или «подсвечивается сразу несколько».

Это отдельная, самостоятельная проблема — не логическая ошибка вычисления активной секции, а чисто визуальная неоднозначность. Она усугубляет любое минорное расхождение из бага №2, потому что пользователю физически невозможно на глаз отличить «реально активное» от «просто под курсором».

Почему это важно: это прямое объяснение репортнутого сценария (скриншот, где «Салаты» зелёная, а видна «Холодные закуски», и одновременно «Вторые блюда» тоже зелёная из-за курсора) — вторая зелёная пилюля почти наверняка была обычным hover-состоянием, а не второй «активной» меткой класса.

Рекомендация: визуально развести состояния, например задать :hover полупрозрачный фон/цветную рамку без сплошной заливки, оставив сплошную заливку только для .active.

### Баг №2 (Major) — смещение (+8) в updateActive() приводит к преждевременному переключению активной пилюли

Файл: menu.js, строки 34-45.

    const updateActive = () => {
      const offset = (jumpNav ? jumpNav.getBoundingClientRect().bottom : 0) + 8;
      let active = sections[0];
      for (const section of sections) {
        if (section.getBoundingClientRect().top <= offset) {
          active = section;
        } else {
          break;
        }
      }
      setActive(active.id);
    };

Замерено в реальном браузере (Chromium, 1440x900):
- jumpNav (.menu-jump) при прилипании к top: 65px имеет реальную высоту примерно 77px, то есть его настоящая нижняя граница (getBoundingClientRect().bottom) примерно 142px от верха вьюпорта.
- Используемый в коде offset = 142 + 8 = 150px — на 8px больше настоящей границы панели.
- .menu-cat имеет scroll-margin-top: 130px (menu.css:86), то есть якорный переход показывает секцию с top примерно 130px, что уже меньше как реального edge (142), так и используемого в скрипте offset (150) — то есть при клике по пилюле верхние ~12px паддинга секции визуально уезжают под липкую панель (не критично: сам заголовок категории отрисовывается ниже, с отступом padding-top: 48-72px, поэтому текст заголовка не обрезается).

Прямой тест плавной прокрутки с шагом 2px в диапазоне перехода «Салаты -> Холодные закуски» показал:

    y=4166: .active (JS) уже = #cold-snacks, реально видимая под панелью секция ещё «Салаты»
    y=4174: .active (JS) = #cold-snacks, реально видимая под панелью секция = «Холодные закуски»

То есть в окне примерно 8px пилюля «Холодные закуски» подсвечивается зелёным, пока пользователь всё ещё видит контент «Салаты» под липкой панелью. Тест на клике по каждой из 12 пилюль (переход + ожидание остановки скролла) показал, что в состоянии покоя расхождений нет — проблема проявляется только во время активной прокрутки, в узком переходном окне на каждой границе секций.

Почему это Major, а не Minor: хотя окно рассинхрона небольшое (единицы-десятки пикселей в зависимости от скорости и рендеринга), это системная, воспроизводимая логическая ошибка (жёстко закодированный +8 не привязан ни к чему реальному), которая присутствует на каждой из 11 границ между категориями и вносит вклад в общее ощущение «мигает не то» — особенно в сочетании с багом №1 (идентичные hover/active стили делают эффект более заметным и сбивающим с толку).

Рекомендация: убрать магическое число +8 и либо не добавлять смещение вовсе (использовать чистый jumpNav.getBoundingClientRect().bottom), либо явно синхронизировать его с scroll-margin-top секций (130px), чтобы точка «переключения активности» совпадала с точкой, на которую реально скроллит браузер при клике по пилюле.

### Баг №3 (Major) — scroll-reveal может оставить контент навсегда невидимым при резком скролле

Файлы: script.js, строки 17-40; style.css, строки 554-557 (.pending { opacity: 0; ... }).

    const revealEls = document.querySelectorAll("[data-reveal]");
    ...
    if ("IntersectionObserver" in window && revealEls.length && !reduceMotion) {
      const io = new IntersectionObserver(
        (entries) => {
          entries.forEach((entry) => {
            if (entry.isIntersecting) {
              entry.target.classList.remove("pending");
              io.unobserve(entry.target);
            }
          });
        },
        { threshold: 0.15, rootMargin: "0px 0px -8% 0px" }
      );
      revealEls.forEach((el, i) => {
        const belowFold = el.getBoundingClientRect().top >= window.innerHeight;
        if (belowFold) {
          el.classList.add("pending");
          el.style.transitionDelay = Math.min(i % 6, 5) * 60 + "ms";
          io.observe(el);
        }
      });
    }

При обычной, плавной прокрутке (колесо мыши, трекпад, клик по ссылкам с scroll-behavior: smooth) это работает нормально — подтверждено тестом (постепенная прокрутка шагами ~500px с паузами полностью снимает pending со всех блоков).

Однако если скролл-позиция меняется одним дискретным скачком, минуя блок целиком (клик по треку скроллбара вне ползунка, резкое перетаскивание ползунка, очень быстрый флик-скролл, программный scrollTo с behavior instant), IntersectionObserver физически не успевает зафиксировать момент пересечения (0.15 порога) для пропущенного блока — колбэк isIntersecting true для него никогда не срабатывает, класс pending не снимается, и блок навсегда остаётся с opacity: 0 (полностью невидим), пока пользователь не прокрутит обратно через этот участок экрана.

Воспроизведено: сразу после загрузки index.html выполнить скачок прокрутки на y=2900 с мгновенным (instant) поведением; через 400-900мс блоки award-badge, trust-stats, trust-quote, section-title(-light), ticket-grid, amenities-note остаются с классом pending, computed opacity = "0". При последующей ручной прокрутке назад через этот диапазон (шаги по 100px) все блоки корректно проявляются — то есть баг не абсолютно перманентный, а «залипает» до тех пор, пока пользователь не пересечёт данную область экрана ещё раз.

Почему это Major: это прямое нарушение принципа, сформулированного в самом ТЗ аудита (reveal-анимация не должна оставлять контент невидимым). Путь воспроизведения (клик по треку/резкое перетаскивание скроллбара, программные скачки, быстрые флики на некоторых трекпадах) — вполне реалистичный обычный сценарий взаимодействия со страницей, а последствие — реально нечитаемый/невидимый блок контента (статистика доверия, награда, контактный блок) до тех пор, пока пользователь случайно не прокрутит обратно.

Рекомендация: не полагаться исключительно на однократное пересечение threshold. Например, при каждом scroll-событии (или через requestAnimationFrame) дополнительно проверять оставшиеся pending-элементы через getBoundingClientRect() и снимать pending, если элемент уже находится выше нижней границы вьюпорта (то есть пользователь его уже проехал), а не только если наблюдатель зафиксировал вход в 15%-й порог.

### Баг №4 (Major) — недостаточный контраст меток веса блюд

Файл: menu.css, строки 166-172.

    .dish-meta span {
      flex-shrink: 0;
      font-size: 0.78rem;
      font-weight: 700;
      opacity: 0.45;
      white-space: nowrap;
    }

Цвет наследуется от --ink (#241a14) на фоне --cream (#fbf8f3). При opacity: 0.45 результирующий контраст примерно 2.8:1 — не проходит порог WCAG 2.1 AA для обычного текста (требуется 4.5:1; даже для «крупного» текста нужно 3:1, а размер здесь 0.78rem примерно 12.5px, что не считается крупным). Это касается всех меток веса/порции («200 г», «320 г», «1 шт» и т.д.) во всех 12 категориях меню — то есть практически на каждой строке блюда на странице menu.html.

Рекомендация: поднять opacity минимум до ~0.62-0.65 (это даёт контраст примерно 4.5:1+, аналогично уже используемому .dish-meta p с opacity 0.62, который проходит проверку), либо задать отдельный сплошной цвет.

### Баг №6 (Minor) — заголовки категорий меню не размечены как заголовки

Файл: menu.html, строки 73-532 (пример строки 74: span class="menu-cat-title" — «Завтраки» с уточнением времени).

На странице menu.html единственный настоящий заголовок — h1 в hero-блоке («Меню хорошего настроения»). Все 12 названий категорий («Завтраки», «Блины», «Первые блюда» и т.д.), визуально оформленные как заголовки разделов (крупный текст, фон, форма «таблетки»), фактически являются span — то есть невидимы для навигации по заголовкам в скринридерах (стандартный способ быстрой навигации незрячих пользователей по длинной странице). На странице также в целом отсутствует какая-либо промежуточная структура заголовков между h1 и футером.

Рекомендация: заменить span class="menu-cat-title" на h2 class="menu-cat-title" (или h3), сохранив все текущие CSS-классы и визуальное оформление.

### Баг №7 (Minor) — aria-label гамбургер-кнопки не отражает состояние «открыто»

Файлы: script.js, строки 5-8; index.html, строка 44; menu.html, строка 37.

    <button class="nav-toggle" id="navToggle" aria-expanded="false" aria-controls="mainNav" aria-label="Открыть меню">

    navToggle.addEventListener("click", () => {
      const open = document.body.classList.toggle("nav-open");
      navToggle.setAttribute("aria-expanded", String(open));
    });

aria-expanded корректно переключается, но aria-label кнопки жёстко зашит в разметке как «Открыть меню» и никогда не меняется на «Закрыть меню», даже когда меню открыто. Для пользователей вспомогательных технологий, которые полагаются на текст ярлыка (а не только на aria-expanded), кнопка всегда озвучивается как «Открыть меню», что вводит в заблуждение в открытом состоянии.

Рекомендация: в обработчике клика дополнительно выполнять navToggle.setAttribute с ключом aria-label и значением «Закрыть меню» / «Открыть меню» в зависимости от состояния open.
